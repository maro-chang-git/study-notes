Kiro — Quality Engineer Reference Map

Features, Setup, and QE Workflow · June 2026

Core Features
⚡ Kiro IDE
Spec-driven agentic IDE built on VS Code · for structured, production-grade AI-assisted development
📋Specs
  • What it isTurns a feature idea into 3 structured docs: Requirements → Design → Tasks
  • RequirementsUser stories with acceptance criteria in EARS notation
  • DesignTechnical architecture, data flow, component structure
  • TasksAtomic implementation steps the agent executes in order
  • For QEWrite specs for test scenarios, regression suites, or data quality checks — not just features
🧭Steering
  • What it isPersistent Markdown context Kiro reads on every interaction
  • ScopeWorkspace (.kiro/steering/) or Global (~/.kiro/steering/). Workspace wins on conflict.
  • Modesalways · auto · fileMatch · manual
  • For QEEncode your test conventions: naming rules, assertion patterns, SQL style, severity taxonomy
🔗Agent Hooks
  • What it isEvent-driven automations that fire on IDE events (file save, create, delete, pre/post task)
  • Trigger typesonFileSave · onFileCreate · onFileDelete · beforeTask · afterTask · manual
  • For QEAuto-generate test stubs when a new API endpoint file is saved; update test docs after spec tasks complete
🎓Skills
  • What it isPortable on-demand knowledge packages following an open standard (.kiro/skills/)
  • ActivationAuto (description match) or manually via /slash command in chat
  • vs SteeringSteering = always-on rules. Skills = specialized know-how loaded only when needed.
  • For QECreate a "SQL-data-quality" skill or "API-test-pattern" skill. Invoke only when writing those tests.
⚡Powers
  • What it isBundles of MCP tools + steering + hooks installed in one click from partner integrations
  • ActivationDynamic — loads when you mention relevant keywords, unloads when not needed
  • PartnersStripe, Neon, Supabase, Figma, Netlify, Terraform/HashiCorp, etc.
  • For QEInstall a DB Power (Neon/Supabase) to let Kiro query your test database during data quality tasks
🔌MCP Servers
  • What it isModel Context Protocol — standard for connecting external tools/APIs to Kiro agents
  • vs PowersMCP loads all tools immediately into context. Powers load dynamically (less token bloat).
  • For QEConnect to your test management tool, BigQuery, or AlloyDB via MCP for live data queries

Priority Setup for QE — What to Configure First

🧭 1. Steering — Always Do This First

## Test Conventions
- All test files: test_*.py (pytest)
- API tests use httpx + pytest
- SQL tests: BigQuery dialect
- Severity: P0 / P1 / P2 / P3
- Never use SELECT * in test queries
- Assert both positive + negative paths
- Data quality checks: completeness,
  accuracy, consistency, timeliness

Save to .kiro/steering/qe-standards.md. Generate a base with "Generate Steering Docs" in the Kiro panel, then customize.

🎓 2. Skills — Build Your QE Library

## Skill: api-test-pattern
description: "Generate pytest + httpx
API test cases with positive, negative,
boundary, and schema validation tests"

## Skill: dq-checklist
description: "Apply data quality checks:
null rate, row count reconciliation,
referential integrity, value range
validation for banking datasets"

Save to .kiro/skills/. Invoke with /api-test-pattern or /dq-checklist in chat.

🔗 3. Hooks — Automate Your Repetitive QE Tasks

## Hook: generate-test-stub
trigger: onFileCreate
filePattern: "src/api/**/*.py"
prompt: |
  A new API file was created.
  Generate a corresponding test stub
  in tests/api/ following QE standards
  from steering. Include happy path,
  error cases, and schema assertions.

## Hook: update-test-docs
trigger: afterTask
prompt: |
  Spec task completed. Update
  TEST_COVERAGE.md with new test cases.

Save to .kiro/hooks/. Replaces the manual step of "now go write the test file."

📋 4. Specs — Use for Any Non-Trivial Test Plan

Prompt Kiro:
"Create Spec: API regression test suite
for payment endpoints covering
idempotency, timeout, and schema
validation scenarios"

Kiro generates:
→ requirements.md (acceptance criteria)
→ design.md (test architecture)
→ tasks.md (executable steps)

Then: run tasks one by one with agent

Don't use specs for tiny tasks. Use them when you need traceability — e.g., a new DQ pipeline test plan.

⚠ Common Mistakes QEs Make with Kiro

⚠ Watch Out For These

  • Skipping Steering setup: Without it, Kiro doesn't know your naming conventions or test patterns. Every output will be generic.
  • Confusing Skills vs Steering: Steering = rules always applied. Skills = expertise loaded on-demand. Don't put everything in steering — it bloats context.
  • Using Specs for tiny tasks: Specs are for planned, multi-step work. For a single test file, just use the chat agent directly.
  • Installing Powers you don't need: Powers activate dynamically — but too many installed = keyword collision noise. Only install what your project actually uses.
  • Not defining Hook conditions precisely: Overly broad hooks fire on every save. Be specific with filePattern to avoid AI running on unrelated files.
  • Treating Kiro like a chatbot: The value is the structured workflow (Steering → Spec → Hook). Using only the chat panel gives you no more than Copilot.
