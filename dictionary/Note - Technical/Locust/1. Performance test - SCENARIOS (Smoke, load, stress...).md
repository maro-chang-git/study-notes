# Performance Test Scenarios Guide

This document explains the different performance test scenarios and when to use them.

| Scenario   | Users | Duration | When to Use                            | Auto/Manual |
| ---------- | ----- | -------- | -------------------------------------- | ----------- |
| **Smoke**  | 5     | 30s      | Quick validation (minimum traffic)     | ✅ Automatic |
| **Load**   | 50    | 2m       | Normal traffic baseline (50~100 users) | 🎯 Manual   |
| **Stress** | 200   | 5m       | Find breaking point (maximum traffic)  | 🎯 Manual   |
| **Soak**   | 100   | 30m      | Stability & memory leaks               | 🎯 Manual   |
| **Spike**  | 500   | 2m       | Traffic burst handling                 | 🎯 Manual   |

## 📋 Test Scenario Types

### 🔍 Smoke Test
**Purpose:** Quick validation that the system works under minimal load

**When to use:**
- After every code deployment
- Before running more intensive tests
- CI/CD pipeline gating (runs automatically)

**Configuration:**
- Users: 5
- Spawn Rate: 1/sec
- Duration: 30 seconds
- Load Pattern: Minimal, just validates endpoints work

**What it checks:**
- ✅ APIs are reachable
- ✅ No critical errors
- ✅ Basic response times
- ✅ Authentication works

---

### 📊 Load Test
**Purpose:** Test performance under expected normal traffic

**When to use:**
- Establish baseline performance metrics
- Regular performance monitoring
- Before releases to validate performance
- After infrastructure changes

**Configuration:**
- Users: 50
- Spawn Rate: 5/sec
- Duration: 2 minutes
- Load Pattern: Steady, normal traffic

**What it measures:**
- ✅ Response times under normal load
- ✅ Throughput (requests/sec)
- ✅ Error rates
- ✅ Resource utilization

---

### 💪 Stress Test
**Purpose:** Find the breaking point of your system

**When to use:**
- Determine maximum capacity
- Find bottlenecks
- Plan for capacity upgrades
- Test autoscaling behavior

**Configuration:**
- Users: 200
- Spawn Rate: 20/sec
- Duration: 5 minutes
- Load Pattern: High, beyond normal capacity

**What it finds:**
- ⚠️ Maximum concurrent users
- ⚠️ Breaking points
- ⚠️ Degradation patterns
- ⚠️ Recovery behavior

---

### ⏱️ Soak Test (Endurance Test)
**Purpose:** Find memory leaks and stability issues over time

**When to use:**
- Before major releases
- After memory management changes
- Validate long-running stability
- Test for resource leaks

**Configuration:**
- Users: 100
- Spawn Rate: 10/sec
- Duration: 30 minutes (or longer)
- Load Pattern: Sustained moderate load

**What it detects:**
- 🔍 Memory leaks
- 🔍 Connection pool exhaustion
- 🔍 Database connection issues
- 🔍 Gradual performance degradation

---

### ⚡ Spike Test
**Purpose:** Test system behavior during sudden traffic bursts

**When to use:**
- Prepare for flash sales / promotions
- Test autoscaling response time
- Validate circuit breakers
- Test rate limiting

**Configuration:**
- Users: 500
- Spawn Rate: 100/sec (very fast)
- Duration: 2 minutes
- Load Pattern: Sudden burst then sustained

**What it validates:**
- 🚀 Autoscaling speed
- 🚀 Queue handling
- 🚀 Error recovery
- 🚀 Graceful degradation

---

## 🎯 Recommended Testing Strategy

### Stage 1: Development
```bash
✅ Smoke Test (every commit)
```

### Stage 2: Pre-Release
```bash
✅ Smoke Test
✅ Load Test (establish baseline)
```

### Stage 3: Pre-Production
```bash
✅ Smoke Test
✅ Load Test
✅ Stress Test (find limits)
⚠️ Spike Test (if traffic spikes expected)
```

### Stage 4: Production Validation
```bash
✅ Smoke Test
✅ Load Test
⏱️ Soak Test (weekly/monthly)
```

## 🚀 Running Tests

### Via GitLab CI/CD

**Automatic (every push):**
- `smoke_test` runs automatically

**Manual (click "Play" button):**
- `load_test` - Click to run
- `stress_test` - Click to run
- `soak_test` - Click to run (takes 30+ min)
- `spike_test` - Click to run

### Locally

```bash
# Set API_KEY first (required)
export API_KEY='your-api-key-here'
export BASE_URL='https://dp-api-uat-gcp.ncb-bank.vn'

# Smoke test
TEST_SCENARIO=smoke bash scripts/run_scenario.sh

# Load test
TEST_SCENARIO=load bash scripts/run_scenario.sh

# Stress test
TEST_SCENARIO=stress bash scripts/run_scenario.sh

# Soak test (long running)
TEST_SCENARIO=soak bash scripts/run_scenario.sh

# Spike test
TEST_SCENARIO=spike bash scripts/run_scenario.sh
```

**🔒 Security Note:** Never commit `API_KEY` to git. Set it as environment variable only.

### Custom Configuration

Override defaults with environment variables:

```bash
# Custom load test
export LOAD_USERS=100
export LOAD_RUN_TIME=5m
TEST_SCENARIO=load bash scripts/run_scenario.sh

# Custom stress test
export STRESS_USERS=500
export STRESS_RUN_TIME=10m
TEST_SCENARIO=stress bash scripts/run_scenario.sh
```

## 📊 Understanding Results

### Response Time Targets & Thresholds

**Default Thresholds (enforced automatically):**
- **P90 ≤ 2000ms** (Pipeline fails if exceeded)
- P95 ≤ 3000ms
- P99 ≤ 5000ms
- Error Rate ≤ 1%

**Recommended Targets by Scenario:**

| Scenario | Target P90 | Target P95 | Target P99 | Error Rate |
|----------|------------|------------|------------|------------|
| Smoke    | < 1s       | < 1.5s     | < 2s       | 0%         |
| Load     | < 2s       | < 3s       | < 5s       | < 1%       |
| Stress   | < 3s       | < 5s       | < 10s      | < 5%       |
| Soak     | < 2s       | < 3s       | < 5s       | < 1%       |
| Spike    | < 5s       | < 8s       | < 15s      | < 10%      |

**⚠️ Important:** Tests will **automatically FAIL** if any API exceeds thresholds!

### Success Criteria

**Smoke Test:**
- ✅ 0% error rate
- ✅ All endpoints responding
- ✅ P90 < 1000ms (recommended)

**Load Test:**
- ✅ < 1% error rate
- ✅ **P90 ≤ 2000ms (enforced)**
- ✅ Response times within target
- ✅ Throughput meets requirements

**Stress Test:**
- ✅ Graceful degradation (no crashes)
- ✅ System recovers after load reduction
- ✅ Error messages are informative
- ⚠️ Higher error rates acceptable (up to 5%)

**Soak Test:**
- ✅ No performance degradation over time
- ✅ Memory usage stable
- ✅ No increasing error rates
- ✅ **P90 remains ≤ 2000ms throughout test**

**Spike Test:**
- ✅ System handles burst without crashing
- ✅ Recovers quickly
- ✅ Rate limiting works properly
- ⚠️ Higher response times acceptable during burst

### Performance Validation

All scenarios include automatic validation:
- Parses metrics from CSV reports
- Checks P90, P95, P99 against thresholds
- Checks error rates
- **Pipeline fails if thresholds exceeded**
- Generates `VALIDATION.txt` report

Override thresholds via environment variables:
```bash
P90_THRESHOLD_MS=3000 TEST_SCENARIO=stress bash scripts/run_scenario.sh
```

## 🔧 Customizing Scenarios

Edit `scripts/scenarios.sh` to customize:

```bash
# Modify load test defaults
load_test() {
    export LOCUST_USERS="${LOAD_USERS:-50}"    # Change 50
    export SPAWN_RATE="${LOAD_SPAWN_RATE:-5}"   # Change 5
    export RUN_TIME="${LOAD_RUN_TIME:-2m}"      # Change 2m
}
```

Or override via GitLab CI/CD variables (no code changes needed):
- `LOAD_USERS=100`
- `LOAD_RUN_TIME=5m`
- etc.

## 💡 Best Practices

1. **Always start with Smoke Test** - Don't waste time on load tests if basic functionality is broken

2. **Run Load Test first** - Establish baseline before stress testing

3. **Don't run Soak Test in CI** - Run manually or scheduled due to long duration

4. **Monitor backend during tests** - Use APM tools to correlate Locust results with backend metrics

5. **Test one scenario at a time** - Don't run multiple scenarios simultaneously

6. **Review results immediately** - Download artifacts and check for anomalies

7. **Adjust for your system** - Default values are starting points, customize based on your capacity

## 🆘 Troubleshooting

**Smoke test fails:**
- Check API endpoints are correct
- Verify API_KEY is valid
- Check network connectivity

**Load test shows high response times:**
- Check backend logs
- Monitor CPU/memory on backend
- Check database performance

**Stress test crashes system:**
- This is expected! It finds limits
- Review at what user count it failed
- Plan capacity accordingly

**Soak test shows degradation:**
- Potential memory leak
- Check connection pool settings
- Review database connection management

**Spike test fails to handle burst:**
- Review autoscaling configuration
- Check rate limiting settings
- Consider queue implementation
